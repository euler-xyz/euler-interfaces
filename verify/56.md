# BNB Smart Chain — Deployed Code Verification

Chain ID: 56 · Contracts in scope: 22 · Bytecode-proven: **22**

**What a proof shows.** Each contract in scope runs the code built from a pinned commit: its on-chain runtime bytecode equals a local build of `repo@commit` with the deployment's compiler settings, after stripping the metadata trailer and masking immutables and the metadata digests of embedded child contracts. Block explorers are not trusted. This is runtime correspondence only: it says nothing about initialization, governance, immutable configuration or deployment safety.

**What is compared with audited code.** Each proven commit is diffed against its component's audited baseline: the fixes-included state of the last audit that reviewed the whole component. Narrower later reviews are linked where they cover a change. Compared: the component's own source paths and the Euler libraries compiled into it (see Embedded libraries). Not compared: third-party dependencies such as OpenZeppelin, LayerZero and Uniswap. Diffs over 400 lines are summarised per file, with a command and a link to see them in full.

**Scope.** 22 contracts on this chain are on the verifier's allowlist. Not covered: `accountLens`, `adaptiveCurveIRMFactory`, `capRiskStewardFactory`, `escrowedCollateralPerspective`, `eulerEarnFactoryPerspective`, `eulerEarnVaultLens`, `eVaultFactoryGovernor`, `eVaultFactoryTimelockController`, `evkFactoryPerspective`, `feeFlowController`, `feeFlowControllerUtil`, `fixedCyclicalBinaryIRMFactory`, `irmLens`, `kinkIRMFactory`, `kinkyIRMFactory`, `oracleLens`, `permit2`, `swapper`, `termsOfUseSigner`, `utilsLens`, `vaultLens` (multisig Safes are not listed).

<details><summary>How to read this report</summary>

- **Pin**: the commit a contract was built from and proven against.
- **Baseline**: the audited commit a component is compared with. **Baseline confidence** says how that commit was established: high = the audit report states the commit, or a tag matches it; medium = derived from tags or fix-PR history; low = inferred from dates.
- **≡ baseline**: the deployed source equals the baseline on the component's paths. **≡ baseline (this contract)**: the component changed, but none of the changed files is compiled into this contract.
- **+N/−M vs baseline**: lines added and removed since the baseline in the files compiled into this contract.
- **predates**: the deployed commit is older than the baseline. Its diff shows what the newer audited code adds: `+` lines are code the deployment does not have.
- **Embedded library**: Euler library code compiled into a contract from a git submodule, compared with the library's own audited baseline.
- **Submodule override**: the build that matches the deployment used a different commit for a submodule than the pin records. The report compares what was compiled.
- **Bytecode proof**: the first 8 hex characters of the sha256 of the normalized runtime code. It is not a commit.
- **Euler note**: a plain-fact summary of a change written by Euler maintainers. It is not an audit finding.

</details>

## EulerSwap

- **eulerSwapV2Implementation** — post-audit functionality change ([diff below](#component-euler-swap-v2-81cf6dc9)):
  > **Euler note** (maintainers' summary, not an audit finding)
  > Beyond the fee mechanism, the post-baseline delta is an EIP-170 code-size refactor that moved management functions into EulerSwapManagement — a separate delegatecall implementation whose address is a public immutable of EulerSwap. Its deployed bytecode is verified in this report from the same euler-swap pin, with the getter value cross-checked against the implementation’s embedded immutable words. The delta also includes ZeroShares handling for EulerEarn-style vaults, and pre-release hardening (pool kept locked during activate) that landed at the eulerswap-2.0 release merge.

- **eulerSwapV2ProtocolFeeConfig** — post-audit functionality change ([diff below](#component-euler-swap-v2-81cf6dc9)):
  > **Euler note** (maintainers' summary, not an audit finding)
  > The deployed V2 release (tag eulerswap-2.0) post-dates the September 2025 Cantina review baseline. Within that delta, protocol-fee handling was redesigned: the reviewed model (fee parameters fixed into each pool at install, 10–25% bounds, permissionless enablement after one year) was replaced by the EulerSwapProtocolFeeConfig singleton, which pools query live on every swap. The fee-config admin can set a default fee and per-pool overrides taking effect immediately, up to MAX_PROTOCOL_FEE = 15% of the LP fee amount (lower than the previously reviewed 25% maximum); zero is allowed. Pre-release hardening is included: the fee-config admin may not be a known EVC sub-account, a non-zero default fee needs a non-zero default recipient, and configuration events are emitted. Per-pool overrides are checked only against the fee bound; an override with a zero recipient pays the default recipient. A pool's own LP fee recipient may not be a known EVC sub-account (checked when the pool is activated, in EulerSwapManagement). Curve and quote math are unchanged by this mechanism.
